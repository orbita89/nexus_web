# Вход и сессия

Поведение бэкенда — в `../nexus_project/documents/modules/auth.md`. Здесь — как это устроено на
фронтенде.

## Где токены

|                   | Где                                  | Почему                                                                    |
| ----------------- | ------------------------------------ | ------------------------------------------------------------------------- |
| Access (15 минут) | в памяти вкладки                     | не переживает перезагрузку, и это нормально: восстанавливается по refresh |
| Refresh (30 дней) | `localStorage`, ключ `nexus.refresh` | общий для вкладок, переживает перезапуск браузера                         |

Почему не httpOnly cookie через сервер SvelteKit: каталог и так рендерится на сервере без
токена (данные публичные), WebSocket всё равно нужен access в браузере, а серверный вариант
переносит гонки обновления на сервер (параллельные SSR-запросы с одной cookie) и добавляет
прокси-слой. Цена решения — refresh доступен скрипту на странице, поэтому XSS у нас критичен:
никакого `{@html}` с пользовательским текстом.

## Очередь обновления

Refresh одноразовый: повторное использование уже заменённого токена бэкенд считает кражей и
отзывает **все** сессии пользователя. Два параллельных обновления с одним токеном разлогинят его.
Поэтому в `src/lib/auth/core.ts`:

1. **Внутри вкладки** — один запрос: все, кому нужен токен, ждут один и тот же promise.
2. **Между вкладками** — Web Lock `nexus.auth.refresh` (`navigator.locks`). Refresh-токен
   читается из `localStorage` уже **внутри** блокировки: другая вкладка могла его заменить.
3. **Новый access рассылается** остальным вкладкам через `BroadcastChannel('nexus.auth')`. Вкладка,
   дождавшаяся блокировки, видит свежий access и не обновляется второй раз.
4. Access, которому осталось меньше 30 секунд, обновляется заранее, до запроса.
5. 401 на запрос с токеном — обновить (если токен ещё не заменён) и повторить запрос один раз.
6. Refresh ответил 401 — сессии нет: токен удаляется во всех вкладках. 429 или 5xx — токен
   сохраняется, запрос падает с ошибкой.
7. Выход — под той же блокировкой: иначе параллельное обновление вернуло бы сессию.

Без `navigator.locks` (не secure context, то есть http не на localhost) работает только очередь
внутри вкладки. В проде — https.

Unit-тесты (`core.spec.ts`) моделируют бэкенд с ротацией и обнаружением кражи; один тест
проверяет, что без блокировки две вкладки действительно разлогинивают пользователя — то есть
защита проверяется по существу.

Известный край: вкладку закрыли, пока запрос refresh в пути, — сервер токен заменил, а новый не
сохранился. Следующий вход с этим токеном выглядит как кража. Решается только на бэкенде
(см. [backend-questions.md](backend-questions.md)).

## Сессия в компонентах

```ts
import { api, session, logout } from '#lib/auth/session.svelte.ts';

session.status; // 'loading' (SSR, первый refresh) | 'guest' | 'authed'
session.user; // UserView | null
```

Сессия восстанавливается в фоне при загрузке (`+layout.ts` → `ensureSession()`), публичные
страницы её не ждут. В шапке, пока `loading`, — пустое место вместо кнопок.

## Защита страниц

Всё, что требует входа, — в группе `src/routes/(protected)/`:

- `+layout.ts`: `ssr = false`, ждёт `ensureSession()`, гостя отправляет на
  `/auth/login?next=<страница>`;
- `+layout.svelte`: вышли здесь или в другой вкладке, сессия кончилась — тоже на вход.

`next` проверяется `safeNext()`: только пути этого сайта, иначе открытый редирект.

## Страницы

| Путь                                     | Что делает                                                                                              |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `/auth/login`                            | email или username + пароль; 403 «email не подтверждён» — предлагает письмо ещё раз; кнопки провайдеров |
| `/auth/register`                         | регистрация → «проверьте почту», повторная отправка. `?resend=1` — только повторная отправка            |
| `/auth/verify-email?token=`              | **из письма.** Подтверждает email и сразу входит                                                        |
| `/auth/email-login`                      | без token — «пришлите ссылку»; `?token=` (**из письма**) — вход                                         |
| `/auth/forgot-password`                  | письмо для сброса                                                                                       |
| `/auth/reset-password?token=`            | **из письма.** Новый пароль; все устройства выходят                                                     |
| `/auth/oauth/callback?code=` / `?error=` | **от бэкенда после провайдера.** Меняет код на токены                                                   |
| `/auth/change-email?token=`              | **из письма.** Подтверждает новый email; вход не обязателен                                             |
| `/settings/accounts?linked=` / `?error=` | **от бэкенда после привязки.** Привязка и отвязка провайдеров                                           |
| `/settings`                              | профиль: username (раз в 30 дней), имя, аватар-ссылка                                                   |
| `/settings/email`                        | смена email; пароль спрашивается, только если он задан (`has_password`)                                 |
| `/settings/security`                     | смена пароля (без пароля — «Задать пароль»: письмо для сброса), сессии, выход на всех устройствах       |

**OAuth.** Кнопки — по `GET /oauth/providers`; пустой список (так в dev) — кнопок и разделителя
нет. Переход к провайдеру — полная навигация браузера на `/api/v1/auth/oauth/{p}/start`, адрес
возврата (`next`) запоминается в `sessionStorage` и используется после `callback`. Привязка из
настроек начинается запросом с токеном (`POST /me/oauth/{p}` → `{url}` → `location.assign`).
Тексты ошибок `?error=` — в `src/lib/auth/oauth.ts`.

## E2E

`e2e/auth.spec.ts`: регистрация → письмо → подтверждение → выход → вход по паролю →
перезагрузка (восстановление по refresh) → выход; вход по ссылке; сброс пароля; закрытая страница
→ вход → возврат + список сессий; битая ссылка; страница входа без провайдеров. Письма читаются
из Mailpit API, из ссылки берутся путь и `token` — поэтому тестам неважно, какой `APP_BASE_URL`
у бэкенда.
