# Теги по разделам и описания тегов

Страница `/tags` — справочник жанров и тем. Сейчас она отдаёт одним алфавитным списком всё
подряд: жанр картин «абстракционизм» стоит рядом с «Боевиком» на 13 328 фильмов, а рядом —
«Антиутопия» с нулём. Понять, к какому типу произведений относится тег, невозможно: жанры
фильмов, сериалов, книг, игр и картин перемешаны. Счётчик `entities_count` — общий по всем
типам, он этого не разводит.

Фронтенд хочет вкладки разделов на `/tags` (Все / Фильмы / Сериалы / Книги / Игры / Картины)
и описание у каждого тега и жанра. Своими силами это не делается:

- `GET /api/v1/catalog/tags` отдаёт `TagWithCount { id, kind: genre|tag, name, slug,
entities_count }` — ни разбивки по типам, ни описания;
- единственный per-kind источник сегодня — фасетный `GET /api/v1/catalog/search/tags?kind=X`
  (`TagHit { slug, name, kind, count }`), но у него `limit` максимум 50. Для полного
  справочника не годится, а собирать список пятью запросами и клеить на фронтенде мы не
  будем: фильтрация каталога — на бэкенде и в Meilisearch.

Изменения добавочные, существующие поля не трогаем.

## 1. Разбивка счётчика по типам

В `TagWithCount` — новое поле:

```jsonc
{
	"id": "…",
	"kind": "genre",
	"name": "Боевик",
	"slug": "action",
	"entities_count": 13328,
	"by_kind": { "movie": 11800, "series": 1500, "game": 28 } // нули можно не отдавать
}
```

- `by_kind: { [EntityKind]: int }` — число **активных** сущностей каждого типа с этим тегом;
  `entities_count` = сумма значений (остаётся как есть, фронтенд на него опирается).
- Считается тем же путём, что и `entities_count` (его держат триггеры). Прецедент формы —
  `ArchiveStats.by_kind`.
- Поле добавить и в `GET /api/v1/catalog/tags/{slug}` (`TagWithCount`) — страница тега
  покажет, сколько в нём фильмов, а сколько книг.

## 2. Фильтр списка по типу сущности

```
GET /api/v1/catalog/tags?entity_kind=painting   → только теги, у которых by_kind[painting] > 0
```

- `entity_kind: EntityKind` (необязательный). Имя параметра — на ваше усмотрение: `kind` у
  этого эндпойнта уже занят значениями `genre|tag`, поэтому нужен другой; фронтенд подстроится
  под то, что вы выберете, — просто назовите его в итоговом сообщении.
- `entities_count` в ответе остаётся общим по всем типам, разбивка — в `by_kind`.
- Алфавитный порядок и состав полей не меняются.

## 3. Описание тега и жанра

Поле `description: string | null` в `Tag`, `TagWithCount`, `TagHit`, а также в `CreateTag` и
`UpdateTag` — чтобы редактировалось в админке (`POST /catalog/admin/tags`,
`PATCH /catalog/admin/tags/{id}`). Образец — `StudioDetail.description`.

- Текст короткий, 1–2 предложения: «Бытовой жанр — сцены повседневной жизни: кухни, рынки,
  мастерские, без героики и мифологии». Пишется руками через админку; генерацию текстов на
  бэкенде не просим.
- `null` — обычное состояние, фронтенд просто не рисует строку.
- Если удобно — сид (`make seed`) с описаниями у нескольких популярных жанров, чтобы было
  на чём проверить.

## Что фронтенд включит после

| Пункт             | Что появится                                                                                    |
| ----------------- | ----------------------------------------------------------------------------------------------- |
| 1 `by_kind`       | вкладки разделов на `/tags`, счётчик словами раздела («391 картина»)                            |
| 2 `?entity_kind=` | список тегов сужается запросом к API, а не фильтрацией на клиенте                               |
| 3 `description`   | описание в карточке тега, под заголовком `/tags/{slug}`, в `<meta description>`, поле в админке |

После слияния: `pnpm api:types`, затем `pnpm verify`.
