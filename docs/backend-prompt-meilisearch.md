# Промт для бэкенда: всё для списков каталога — в Meilisearch

Решение пользователя (2026-10-15): **любая сортировка, фильтрация и поиск — только через
Meilisearch**, не через PostgreSQL. Фронтенд уже перевёл на `GET /search` разделы (`/films`),
главную, теги и фильмы студии: `GET /entities?kind=movie&sort=recommended&limit=24` на dev шёл
6–8 с, тот же список из Meilisearch — 30–130 мс. Чего в индексе нет, фронтенд не добирает из БД —
ниже то, что нужно добавить. Ниже — промт для сессии Claude Code в `/home/dev/nexus_project`.

Проект Nexus — модульный монолит на Rust (axum, sqlx, PostgreSQL, Meilisearch, utoipa). Перед

не списки. Если для списка не хватает данных — добавить их в документ индекса.

Общее:
- Контракты меняются только добавочно (новые поля, параметры, эндпоинты); documents/api/*.json
  обновить — фронтенд генерирует типы из них (pnpm api:types).
- Настройки индекса ставятся при перестройке (теневой индекс, как сейчас); после выкладки —
  перестройка. Документ обновляется там же, где сейчас (publish::run, update_index).
- Один пункт — один коммит, после каждого make ci зелёный. Порядок — по важности.

1. ТОЧНЫЙ TOTAL И ПОТОЛОК 1000 (главное). Сейчас GET /search без запроса отдаёт total = 1000
   вместо 119 773, offset ≥ 1000 — пусто; фронтенд вынужден писать «Больше 1 000 фильмов», и
   пользователь это не принимает: нужно настоящее число. Причины две:
   - в entity_settings нет pagination.maxTotalHits, у Meilisearch по умолчанию 1000 — дальше он
     не считает и не листает. Поставить "pagination": {"maxTotalHits": 500000} (с запасом на
     рост горячего слоя) у индекса сущностей и людей;
   - total берётся из estimatedTotalHits (offset/limit) — это оценка. Точное число Meilisearch
     (у нас v1.15) отдаёт в режиме page + hitsPerPage: поле totalHits, exhaustive. Перевести
     запрос к Meilisearch на page/hitsPerPage (offset и limit API делятся на страницу: фронтенд
     всегда шлёт offset кратный limit) или, если так неудобно, — вторым дешёвым запросом
     limit 0 + page 1 + hitsPerPage 1 ради totalHits. Контракт API не меняется: total в
     Page<EntitySummary> просто становится точным (описание в схеме — «всего найдено»).
   Проверить: GET /search?kind=movie → total 119 773 (= GET /entities?kind=movie), ?tag=horror →
   10 506, ?offset=5000 — не пусто, с q — точное число совпадений; время ответа с сортировкой и
   без — замерить и записать в catalog.md. Если точный счёт по 120 тыс. заметно медленнее
   (больше ~100 мс) — сказать до выкладки.

2. ОЦЕНКИ NEXUS В ИНДЕКСЕ. GET /entities умел sort=popular (больше оценок Nexus) и rating (средняя
   оценка Nexus); в GET /search их нет, и фронтенд эти порядки убрал. Добавить в документ
   nexus_ratings_count и nexus_rating_avg (sortableAttributes), в SearchSort — popular и rating
   (как было у EntitySort: popular — по числу оценок, rating — по средней, без оценок в конце).
   Оценки живут в модуле social: обновлять документ по событию оценки через границу модулей
   (как принято в for-other-modules.md) или пачкой по расписанию (раз в несколько минут) —
   выбрать и описать в catalog.md.

3. ФИЛЬТР ПО ЛЮДЯМ. Сейчас person/role у GET /search — заглушка 503 person_filter_unavailable.
   Добавить в документ из титров people (slug'и всех участников) и credits ("director:slug",
   "actor:slug" — роль и человек), оба в filterableAttributes; person → people = "slug",
   person+role → credits = "role:slug". Заглушку убрать. Фронтенд уже шлёт person и role.

4. СТУДИЯ ПО SLUG. Фильтр studio — точное название; страница студии из-за этого делает два
   запроса подряд (GET /studios/{slug} → название → GET /search?studio=). Добавить в документ
   studio_slugs (filterable) и параметр studio_slug у GET /search; в ответе
   GET /search/studios — slug рядом с name (фронтенд сделает ссылки на /studios/{slug} в
   подсказках).

5. АРХИВ — В MEILISEARCH. Архив (~1,07 млн фильмов) сейчас в Tantivy: только по названию,
   limit ≤ 20, offset ≤ 1000, без счётчика и без фильтров; «весь архив» фронтенд получает
   запросом q=* — 1,2–2,9 с на счёт. По правилу пользователя поиск должен быть в Meilisearch.
   Предложение: отдельный индекс archive с документом той же формы, что у сущностей (slug, title,
   original_title, kind, release_date, year, release_ts, cover_url, popularity, tmdb_id) и тем же
   набором фильтров и сортировок, что применимы; adult из TMDB — не индексировать (сейчас в
   верху q=* по популярности фильмы для взрослых). В GET /search — параметр archive=include:
   одна выдача, один total и одна пагинация (federated multi-search Meilisearch, у архивных
   элементов is_archived: true) — тогда фронтенд уберёт отдельные запросы к архиву. Возврат
   фильма (restore/promote) удаляет документ из archive и добавляет в основной. Оценить объём
   (диск, память, время индексации 1 млн документов) и записать в catalog.md; если по объёму
   не годится — сказать до реализации.

6. «РЕКОМЕНДАЦИИ» (GET /entities/{slug}/similar) — сейчас SQL по общим тегам. Сделать через

7. АДМИНКА. GET /admin/entities?q= и GET /people?q= (редактор титров, список людей в админке)
   ищут по БД. Сущности: в документ — active/visible (filterable); публичный GET /search всегда

## Что фронтенд сделает после бэкенда

1. Точный total — счётчик «119 773 фильма» (с архивом — сумма), «Показать ещё» — по всему
   каталогу; `SEARCH_MAX_TOTAL`, «Больше …» и «Около …» уйдут.
2. Оценки Nexus — вернуть «Больше оценок Nexus» и «Оценки Nexus» в `LIST_SORTS`.
3. Люди — ничего: фильтр уже шлётся, пропадёт плашка «скоро заработает».
4. Студия по slug — один запрос на странице студии, ссылки в подсказках студий.
5. Архив — `archive=include` вместо отдельных запросов (`archive.svelte.ts`), общий счётчик и
   фильтры по году и студии вместе с архивом.
   6–7. Рекомендации — без изменений на фронтенде; админка — поиск через новый параметр.
